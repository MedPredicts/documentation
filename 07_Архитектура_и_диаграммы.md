## 1. Архитектурная позиция и подтверждения

MedPredict рассматривается как учебный исследовательский веб-прототип с потенциально тремя независимыми задачами оценки или прогнозирования числовых показателей. Репозиторий frontend содержит реализованное приложение на React + TypeScript + Vite с локальным демонстрационным адаптером и HTTP-адаптером. Демо возвращает фиксированное значение 134,2 мм рт. ст. независимо от ввода и никогда не вызывает обученную модель. Наличие HTTP-клиента и тестовых ответов не доказывает, что реальная интеграция работает.

Backend на Java / Spring Boot описан в его README: разделение на Controller, Service и PredictionModel, валидация по схеме, локализованные сообщения об ошибках, Swagger / OpenAPI, список разрешённых источников CORS, без базы данных и без сохранения. По умолчанию модель не подключена, и оба endpoint возвращают 503 MODEL_UNAVAILABLE; отдельный demo-профиль возвращает фиксированное значение. Артефакты обученных моделей и результаты экспериментов не переданы, поэтому предобработка, вывод модели и M1 / M2 / M3 показаны как предлагаемые. База данных, очередь и отдельный микросервис на Python не объявляются существующими.

Источники фактов: требования университета; AGENTS.md; src/types.ts, src/App.tsx, src/hooks/usePrediction.ts, src/config/, src/api/, src/components/, src/pdf/report.ts; предварительный контракт API и тесты; README backend. Спецификация требований определяет FR-01–FR-13 и NFR-01–NFR-09. Сохранённые docs/architecture.md и docs/diagrams/ не заменяются.

Опубликованный frontend — одностраничное демо. Страницы входа, аккаунта и истории, описанные ниже, относятся к расширенному интерфейсу по макету Figma и отсутствуют в опубликованной ветке main.

Пользователь работает с браузерным прототипом: вводит синтетические примеры, видит состояние, результат или ошибку и может экспортировать PDF. В демо-режиме нет вычислений модели и передачи показателей на сервер. В реальном режиме клиент обращается только к явно настроенному API; сквозная интеграция по-прежнему не подтверждена.

Граница системы охватывает существующий frontend и backend. Кандидаты данных и процесс обучения находятся вне пути пользователя. Источники и права использования данных, правила отбора и артефакты моделей необходимо утвердить. Ввод пользователя в демо не является обучающей выборкой. Локальный PDF — отдельный экспортируемый документ, который может содержать введённые показатели и по действию пользователя остаётся на его устройстве.

### 4.2 Компоненты backend и предлагаемый путь модели

Целевой путь обработки: frontend на React, REST API на Spring Boot, независимая проверка входа и предобработка, вывод модели, ответ API, проверка ответа на клиенте, интерфейс результата.

| Компонент | Требуемая ответственность | Состояние / что предстоит решить |
| --- | --- | --- |
| Spring Boot REST (controller, service) | Принять запрос, проверить формат, отдавать метаданные, ошибки, совместимость версий | Описан в README backend как реализованный (GET model/info, POST predictions, Swagger UI, список разрешённых источников CORS). Остаётся: формальное утверждение GET / POST / 400, TLS, среды, доступ, эксплуатация |
| Валидация и предобработка | Независимая серверная валидация; тот же порядок признаков, пропусков, единиц и преобразований, что и при обучении | Валидация по схеме из метаданных модели описана как реализованная. Код / артефакты предобработки, их версия и тесты ещё предстоит передать; параметры обучаются только на train |
| Вывод модели (PredictionModel) | Вызвать утверждённую модель и привязать ответ к фактически использованной версии | Интерфейс существует с реализацией «недоступно» по умолчанию и демонстрационным провайдером. ONNX в Java, отдельный вывод на Python или другой путь не выбраны |
| Ответ API | Число, корректная единица, версия при наличии, безопасное сообщение об ошибке | DTO описаны; эталонные ответы и допуски сравнения ещё предстоит задать; без оснований клинической интерпретации нет |
| M1 / M2 / M3 | Независимые артефакты, схемы признаков и границы каждой задачи | Ни один не реализован; обучение, оценка, выбор данных и многомодульный контракт впереди |

База данных и постоянное хранилище не нужны для текущего минимального сценария «запрос — ответ», и README backend подтверждает, что их нет. Если будут согласованы аккаунты или история, потребуется отдельная архитектура доступа, хранения и удаления. Их нельзя считать решёнными только потому, что есть экраны.

| M3 Glucose forecasting | Краткосрочный прогноз на подходящем продольном наборе PhysioNet; временной базовый метод и подходящая нейронная сеть, возможно LSTM | Нужны метки времени, окно, горизонт, разбиение по пациентам / времени, правила пропусков и согласованный контракт последовательности | Не реализован; набор данных, горизонт и единицы не утверждены |

HTTP-сервис и политика ошибок могут быть общими, но не автоматически признаки, единицы, предобработка, метрики или веса. Конкретный вызов вывода использует один выбранный совместимый модуль и не запускает все три сразу. Производительность и качество между модулями не переносятся.

## 6. Текущий контракт и предлагаемое развитие

Со стороны frontend PredictionApi имеет два метода: getModelInfo(signal) и predict(input, signal). HTTP-адаптер использует GET /api/v1/model/info и POST /api/v1/predictions. README backend описывает оба endpoint, поэтому прежнее замечание о том, что GET был лишь предложением frontend, на практике устарело; формальное согласование между Оралханом и Санатом всё же стоит зафиксировать. Данный документ не меняет путь или тело запроса.

Метаданные задают indicatorName, unit, decimalPlaces, непустой массив fields и необязательный modelVersion. Числовые поля отправляются как числа JSON, списочные поля — как строки. Ответ содержит конечное predictedValue, непустую unit и необязательные modelVersion / disclaimer. Единица ответа должна совпадать с единицей метаданных. Клиент не подставляет версию из метаданных вместо отсутствующей версии конкретного результата.

Для трёх модулей каталог, идентификаторы, доступность, версионирование и выбор схемы ещё необходимо согласовать отдельно. Рабочий endpoint /modules, moduleId или иное расширение не вводятся как факт. Текущая форма number / select не считается готовым контрактом временного ряда для M3. За любым расширением, после согласования командой, следует обновление docs/api-contract.md, типов, тестов, требований и диаграмм.

## 7. Последовательность сценария реального режима

1. Проверить конфигурацию среды и явно выбрать реальный режим. Запросить метаданные GET и разобрать недоверенный JSON; при ошибке форма и POST недоступны, разрешён явный повтор GET. С профилем backend по умолчанию этот шаг возвращает 503 MODEL_UNAVAILABLE, и форма корректно остаётся недоступной.

2. Показать поля из метаданных. Перед отправкой разобрать и проверить ввод; при ошибке привязать сообщения к полям и перевести фокус на первое неверное поле.

3. После явного действия отправить один POST и зафиксировать проверенный снимок ввода. Повторный клик во время запроса не создаёт второй POST.

4. Сервер независимо проверяет ввод, применяет согласованную предобработку и вызывает конкретный версионированный артефакт. Эта часть ещё не подтверждена реальной интеграцией (demo-профиль backend лишь возвращает фиксированное значение).

5. Получить ответ; проверить структуру, конечность числа и единицу. Показать результат, снимок ввода и постоянное предупреждение. Недопустимый ответ обрабатывается как ошибка.

6. При отмене, изменении данных или навигации отменить ожидание и игнорировать запоздавший ответ. Отмена HTTP на клиенте сама по себе не доказывает, что вычисление на сервере остановилось.

7. По отдельному действию экспортировать готовый результат в PDF без нового POST. После правки формы или навигации прежний результат скрывается.

## 8. Границы доверия, приватность и отказоустойчивость

Показатели живут в памяти React в пределах текущей загрузки страницы. Frontend не сохраняет их в localStorage / sessionStorage, URL, аналитике или журналах приложения. После перезагрузки ввод теряется. Это ограничение frontend, а не обещание, что копий нет на уровне браузера, ОС или стороннего сервера. Экспортированный PDF — явное исключение из отсутствия постоянного пользовательского документа.

Демо не отправляет показатели по сети. Реальный режим отправляет их на настроенный API, поэтому журналы сервера, хранение, доступ и обработка ошибок требуют отдельной проверки. README backend сообщает, что у него нет базы данных, журналирования тела запроса и сохранения прогнозов, и указывает, что трассировка тел запросов / ответов должна оставаться выключенной для медицинских входных данных. Настройки VITE_* видны в клиентской сборке и не предназначены для секретов. Для реальной публикации необходимо согласовать TLS, разрешённые источники / CORS и политику обработки данных. Данные пользователей автоматически для обучения не используются.

Надёжность клиентского пути обеспечивают явные состояния, тайм-аут по умолчанию 15 000 мс, отсутствие автоматического повтора POST и переключения на демо, AbortController и проверка текущего запроса. Ошибка по известному полю привязывается к нему; неизвестное поле сообщает о несовместимом ответе. Это проверяемые свойства клиента; доступность сервера и время вывода из них не выводятся.

| AR-05 | Реализовывать три модуля независимо и поэтапно | Разные задачи, данные и временная структура | Сначала согласовать один вертикальный модуль, затем расширять |
| AR-06 | Не добавлять базу данных, аутентификацию или историю в обязательный конвейер | Функции отключены, политики хранения нет; у backend её тоже нет | Отдельное согласование и требования до включения |
| AR-07 | Доступность модулей и временной API — будущий контракт | Текущий GET описывает один набор полей | Выполнить D6 спецификации, затем менять код / тесты |
| AR-08 | Frontend должен отправлять Accept-Language, чтобы локализованные ошибки backend совпадали с языком интерфейса | Backend локализует ошибки по Accept-Language (kk, ru, en); адаптер frontend его не отправляет | Добавить заголовок и тест; согласовать резервный язык |

Рекомендуемый порядок: научная постановка и данные, затем базовый метод и MLP первого утверждённого модуля, затем воспроизводимая оценка, затем реальный вертикальный API, затем второй модуль, затем временной модуль, если данные подтверждены, затем многомодульный UI. Это план, а не отчёт о выполненной работе.

## 11. Редактирование и проверка артефактов

Для каждого рисунка хранятся несжатый XML .drawio, просматриваемый .svg и растровый .png. Файл .drawio открывается в совместимом редакторе diagrams.net; он содержит отдельные узлы, связи, подписи и геометрию, а не одну вставленную картинку. SVG и PNG создаются из тех же подписей и координат. После изменения исходника изображения нужно экспортировать заново и проверить соответствие требований, состояний и путей API.

В версии от 21 октября три диаграммы обновлены с учётом README backend (зелёным цветом обозначен backend по его описанию, синим — реализованный frontend, пунктиром — запланированное).
