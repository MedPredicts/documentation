## 1. Назначение и основа

Документ задаёт проверяемые требования к учебному исследовательскому прототипу MedPredict и разделяет существующую реализацию, подготовленные клиентские адаптеры и будущие функции. Основа: требования, предоставленные университетом; текущие исходники и документация frontend/backend/ML; [сравнение систем](04_Сравнение_существующих_систем.md); план оценки из исходного комплекта (документ 09; в этот PR не входит). Настоящая редакция не меняет API и не объявляет предложения утверждёнными требованиями.

Система предназначена для изучения оценки и прогнозирования числовых медицинских показателей. Она не является утверждённым средством диагностики, назначения лечения или индивидуальных клинических решений. Демонстрации и технические проверки используют синтетические примеры; обучение M2 выполнено на обезличенных public-use данных NHANES. Это не разрешение собирать показатели пациентов через приложение.

Требования к модели, её качеству и развёртыванию не считаются выполненными только потому, что есть интерфейс или возвращается фиксированный демонстрационный ответ.

### 2.1 Один реализованный и два будущих модуля

| ID / задача | Кандидат данных | Метод и результат | Состояние / требуемое решение |

У модулей разные целевые переменные, признаки и протоколы оценки. Общие компоненты архитектуры не означают единую модель. Текущая real-форма реализует M2: возраст, пол, ИМТ, общий холестерин и глюкоза плазмы натощак; оба лабораторных показателя — в ммоль/л. Отдельный demo остаётся фиксированным примером. M2 оценивает текущее САД, не измеряет давление пациента и не прогнозирует будущее давление или риск заболевания. HTTP-контракт описывает один активный набор метаданных и результат; API выбора M1 / M2 / M3 не определён.

### 2.2 Пользователи и границы

Основные пользователи прототипа — участники демонстрации и потенциальные представители учебной и исследовательской аудитории. Их реальные задачи и потребности нужно проверить исследованием пользователей; по одному описанию проекта они не объявляются подтверждёнными. Команда и руководитель — участники проверки проекта. Клинические пользователи и пациенты не считаются подтверждённой целевой группой. В репозитории есть заполненные записи интервью из исходного комплекта (документ 02; в этот PR не входят); происхождение, согласие участников и метод проведения в этой правке не проверялись. Наличие записей не доказывает клиническую полезность или рыночный спрос. Отдельные материалы synthetic-market-study остаются вымышленной симуляцией.

Текущие границы включают ввод, валидацию, запрос, отображение результата, ошибки, отмену, локализацию и локальный PDF. Будущие модельные модули добавляются поэтапно. Вне текущего минимального объёма: диагностика и лечение, клиническая сертификация, электронные медицинские карты, автоматический сбор данных пациентов, онлайн-дообучение на пользовательском вводе, рабочие аккаунты и постоянная история.

## 3. Обозначения и управление требованиями

- Must: обязательно для соответствующего этапа. Should: желательно для прототипа. Later: отдельный этап после согласования.

- Коды статуса. R: реализовано в указанной области; для M2 включает frontend, backend и ONNX. A: историческое обозначение только клиентского адаптера, сохранено для чтения предыдущей версии. P: предложено. O: функция отключена, полная реализация отложена.

- Зависимости. D1: согласованные цель, признаки, единицы и данные от Али. D2: согласованный контракт и работающий сервис Spring Boot от Оралхана. D3: обученная версионированная модель и воспроизводимый эксперимент от Али. D4: согласованные безопасность, приватность и среда. D5: решения руководителя и реальные свидетельства пользователей. D6: отдельный контракт выбора и доступности модулей. Для M2 D1–D3 технически представлены; формальное человеческое согласование и production-часть D4 не подразумеваются по факту реализации.

- Ссылка на тест означает существующий способ проверки в репозитории; результат его запуска должен фиксироваться отдельным протоколом. Для P называется будущая проверка.

При изменении требования обновляются связанные критерии, тесты, документ API и диаграммы. Существующие FR-01–FR-11 и NFR-01–NFR-08 сохранены для совместимости; новые идентификаторы добавлены в конец. Утверждение документа ещё ожидается.

## 6. Контракт и данные

Реализованный контракт M2 остаётся в силе: GET /api/v1/model/info возвращает упорядоченные метаданные полей, единицу результата, число десятичных знаков и версию модели; POST /api/v1/predictions принимает плоский объект JSON. Схема M2 задаётся metadata артефакта: age, sex male / female, bmi, totalCholesterol, glucose; входные диапазоны не объявляются медицинскими нормами. Данный документ не добавляет endpoints, поле moduleId или несовместимую структуру запроса.

Ответ GET содержит indicatorName, unit, decimalPlaces, fields и необязательный modelVersion. Необязательные predictionType и demo в ответе POST строго проверяются; legacy modelVersion demo-example сохраняет маркировку demo. Это описание существующей границы, а не расширение API. POST использует ключи полей GET и возвращает конечное predictedValue, unit и необязательные modelVersion / disclaimer. Версия из GET не подставляется вместо отсутствующей версии конкретного ответа. Числовые диапазоны берутся только из метаданных артефакта и отражают поддержку train, а не медицинские нормы. GET / POST поддерживают необязательные строго проверяемые predictionType и demo: M2 — estimated_current_measurement и demo:false, фиксированный пример — demo:true. Версия результата не подменяется версией GET.

Таблица 4. Согласованное поведение при ошибках

| Ситуация | Ответ backend (по его README) | Обработка во frontend |
| --- | --- | --- |
| Корректный запрос, onnx-профиль | 200 с оценкой текущего САД, unit, modelVersion, predictionType estimated_current_measurement, demo:false | Показать исследовательскую оценку и ограничения; не называть измерением или будущим прогнозом |
| Корректный запрос, demo-профиль | 200 с predictedValue 134.2, unit, modelVersion demo-example, предупреждение DEMO | Показать результат; пометить как фиксированный пример |
| Ошибка валидации полей | 400 {"error": "VALIDATION_ERROR", "fields": [...]} | Привязать каждое сообщение к полю; неизвестные имена полей отклонять как несовместимый ответ |
| Некорректный JSON, неизвестные / дублирующиеся ключи, хвостовой JSON | 400 INVALID_REQUEST без возврата отправленных значений | Показать общую ошибку запроса |
| Модель не подключена или недопустимый вывод | 503 MODEL_UNAVAILABLE; автоматического переключения нет | Держать форму недоступной или показать «временно недоступно»; никогда не переключаться на демо |
| Непредвиденный сбой | 500 SYSTEM_ERROR без деталей исключения | Показать общую ошибку сервера |
| Неверный тип содержимого | 415 | Показать общую ошибку запроса |

Для M3 потребуется отдельный контракт временного ряда: порядок и метки времени, пропуски, единицы и горизонт. Текущих типов number / select недостаточно для произвольной временной последовательности. Расширение контракта выполняется вместе с тестами и решениями о миграции.
