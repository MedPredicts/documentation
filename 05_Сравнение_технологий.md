## 1. Основа и границы анализа

Изучены репозиторий frontend (AGENTS.md, package.json, README, конфигурация показателя, HTTP-адаптер, контракт API), README backend, предоставленный командой, и более раннее сравнение технологий. Данный документ расширяет прежний анализом моделей и путей интеграции.

Frontend реализован на React + TypeScript + Vite. В package.json заявлены React ^19.2.0, TypeScript ~5.9.3, Vite ^7.2.0, jsPDF, Vitest и Playwright. Это заявленные диапазоны, а не утверждение о последних версиях или серверной среде. HTTP-адаптер и проверка JSON есть, но работа с реальной моделью не доказана. Фиксированный демонстрационный ответ не является выводом модели.

README backend описывает сервис на Java 17+ / Spring Boot / Maven (springdoc 2.8.13, Spring Boot 3.5) с GET /api/v1/model/info и POST /api/v1/predictions, серверной валидацией, локализованными ошибками, Swagger UI, списком разрешённых источников CORS, без базы данных и без журналирования тела запроса. По умолчанию оба endpoint отвечают 503 MODEL_UNAVAILABLE; отдельный demo-профиль возвращает фиксированное значение 134,2. Обученная модель, ноутбуки и результаты экспериментов не переданы. Поэтому ниже Spring Boot — направление команды, под которое уже есть код, а MLP / LSTM и подходы к выводу модели — кандидаты.

Рассматриваются три значимых решения по три альтернативы. Критерии одинаковы по смыслу: сложность разработки, совместимость, сопровождение, ожидаемая вычислительная стоимость, тестирование, соответствие ролям команды, развёртывание и ограничения. Утверждения об ожидаемой сложности — инженерные выводы для данного проекта, а не измеренные рейтинги.

## 2. Решение 1: основной backend

Техническая возможность REST-контроллеров и JSON подтверждается руководством Spring; OpenAPI и проверка данных — документацией FastAPI; модульная организация приложения на TypeScript и средства валидации — документацией NestJS (источники T1–T5).

Таблица 1. Альтернативы основного backend

| Критерий | Java / Spring Boot | Python / FastAPI | Node.js / NestJS |
| --- | --- | --- | --- |
| Сложность разработки | REST-контроллеры и DTO; необходимо согласовать ошибки и валидацию | Типизированные схемы входа; весь серверный сценарий всё равно нужно писать | Контроллеры, модули, провайдеры и валидация во время выполнения; одного типа TypeScript недостаточно |
| Совместимость | Соответствует направлению команды; frontend обращается по HTTP / JSON | Удобно, если среда модели — Python; клиентский JSON совместим | Совместим по HTTP / JSON; общий язык с frontend не делает сетевой ответ проверенным |
| Сопровождение | Один backend на Java, если вывод выполняется в JVM; артефакт модели версионируется отдельно | Возможна единая среда Python для модели и API, но её зависимости нужно фиксировать | Один серверный проект на TypeScript; связь с моделью на Python / Java остаётся отдельным решением |

| Тестирование | Контроллеры, DTO, ошибки, CORS, модель и контракт. | Роли команды | Ответственность Оралхана уже назначена в проекте, код существует | Нужно было бы согласовать, кто сопровождает API на Python: Оралхан или Али | Потребовалась бы смена серверного стека и ответственного; опыт команды не установлен |
| Развёртывание | Приложение Java; официальный пример использует исполняемый JAR; по README HTTPS настраивается на границе развёртывания | Сервис на Python с зафиксированными пакетами и процессами | Приложение Node с серверными зависимостями; наличие Node для Vite — это не backend |
| Ограничения | Формат модели должен быть совместим с JVM, иначе нужен отдельный сервис вывода | Замена основного backend меняет договорённость команды; доступность пакетов не гарантирует безопасность | NestJS в репозитории нет; переход не обоснован выявленной потребностью |

Предлагаемое решение. Сохранить Java / Spring Boot как основной backend в соответствии с распределением ответственности; существующий код backend это поддерживает. FastAPI остаётся допустимым вариантом для внутреннего сервиса вывода на Python, если этого потребует выбранная модель. Оснований переходить на NestJS сейчас нет. Это решение о стоимости интеграции и ответственности, а не о безусловном превосходстве Java.

Предстоит подтвердить с Оралханом: версии Java / Spring, формальное утверждение формата GET с информацией о модели (реализован в backend, но предложен сначала frontend), проверки единиц, CORS и способ вызова модели. История и аутентификация не входят в архитектуру как готовые функции; README backend прямо указывает, что они вне границ проекта.

## 3. Решение 2: методы моделирования по задачам

MLP и LSTM не следует выбирать как взаимозаменяемые «более точные нейронные сети». Выбор зависит от структуры наблюдения. Линейные модели и MLP принимают табличный вектор признаков; LSTM предназначена для последовательности и имеет рекуррентное состояние. Эти возможности подтверждены первичной документацией линейных моделей scikit-learn, MLPRegressor и слоя LSTM в Keras (T13–T15). Их точность на данных MedPredict не измерялась.

Таблица 2. Три группы методов; выбор уточняется внутри каждого модуля

| Критерий | Простые базовые методы | MLP | LSTM |
| --- | --- | --- | --- |
| Сложность разработки | Таблицы: среднее и линейная / Ridge-регрессия; ряды: последнее значение и простой тренд | Настройка слоёв, регуляризации, оптимизатора и ранней остановки | Дополнительно окна, порядок времени, частота, пропуски, состояние и горизонт |
| Соответствие задаче | Обязательная точка сравнения для всех модулей; конкретный базовый метод зависит от данных | Кандидат для Diabetes и NHANES; для ряда может работать с фиксированным окном | Кандидат для продольного ряда глюкозы; временная структура не предполагается в табличных строках |
| Сопровождение | Явный набор признаков / коэффициенты или правило прогноза | Версии весов, предобработки и гиперпараметров | Версии весов плюс правила окон, состояния, меток времени и доступности входов |
| Ожидаемая стоимость | Вычислительный бюджет легко контролировать; задержку всё равно нужно измерять | Стоимость зависит от размера сети и батча; выигрыш по ошибке неизвестен | Длина последовательности и архитектура влияют на стоимость; необходимость GPU не установлена |
| Тестирование | Одно разбиение, без утечки, MAE / RMSE и контроль единиц | Те же данные / разбиение; масштабирование, начальные значения генератора, сходимость и переобучение | Временное и, где нужно, межпациентное разбиение; без будущих признаков и без перекрывающихся окон |
| Роли команды | Али фиксирует протокол и обучает базовый метод до нейронной сети | Али выбирает архитектуру в рамках согласованного бюджета поиска | Али и руководитель сначала подтверждают пригодность продольных данных |
| Развёртывание | Коэффициенты / артефакт или правило; нужна та же предобработка | Экспорт / загрузка модели и проверка равенства вычислений | Поддержка последовательных входов; текущий API формы временной ряд не описывает |
| Ограничения | Линейной зависимости и простого продолжения ряда может быть недостаточно | Нелинейность не гарантирует улучшения; результаты зависят от данных и настройки | Последовательность нельзя создавать произвольной сортировкой людей; дополнительную сложность должен оправдывать эксперимент |

Таблица 3. Постановка по модулям и предварительный выбор

| Модуль | Допустимая цель и данные | Методы для сравнения | Что нужно до выбора |
| --- | --- | --- | --- |

| Systolic Blood Pressure Estimation | Систолическое АД в мм рт. ст. из NHANES; пример кодбука BPX_J содержит несколько последовательных измерений за обследование (T8) | Среднее / линейная или Ridge-регрессия и MLP | Выбрать цикл, популяцию, признаки и правило формирования цели; повторные измерения одного визита не доказывают долговременную динамику |
| Glucose Forecasting | Будущая глюкоза, если существует подходящий продольный набор PhysioNet; конкретный ресурс и горизонт не выбраны (T9) | Последнее значение / простой тренд, MLP на окне, LSTM как кандидат | Проверить доступ, лицензию, пациентов, частоту, пропуски, горизонты, длину рядов и допустимые признаки; не обещать 30 минут по аналогии с устройством |

Число наблюдений Diabetes приведено из документации набора данных, а не из загрузки или запуска обучения. Для NHANES справочник BPX_J иллюстрирует проверяемую структуру переменных и не означает, что цикл 2017–2018 утверждён для проекта. Каталог PhysioNet сам по себе не подтверждает пригодность конкретных данных по глюкозе.

Предлагаемое решение. Первым экспериментом сделать базовый метод и небольшой MLP для Diabetes, затем распространить воспроизводимый протокол на NHANES. Glucose Forecasting реализовывать после отдельного решения о данных. Предпочтение MLP / LSTM в теме диплома не позволяет отказаться от базового метода или сообщать выдуманное улучшение. Если сеть не превосходит базовый метод на утверждённом тесте, отрицательный результат описывается честно; условия дальнейшей работы вытекают из анализа ошибок.

Разбиение данных выполняется до любой обучаемой предобработки. Для строгого эксперимента Diabetes вопрос о сырых данных должен быть решён явно: load_diabetes по умолчанию возвращает масштабированные признаки, а scaled=False даёт исходный вид, чтобы преобразования подбирались только на обучающей части (T7). Преобразования, оценённые на всей выборке, нельзя выдавать за подобранные только на train.

## 4. Решение 3: интеграция модели с backend на Java

ONNX Runtime предоставляет Java API для запуска моделей ONNX. Его существование не гарантирует, что экспортируется любой оценщик: документация scikit-learn указывает на неполную поддержку и дополнительные затраты для пользовательских преобразований (T10, T11). В качестве третьего технически возможного пути рассмотрен PMML с JPMML-Evaluator: официальный проект описывает вычисление регрессий и нейронных сетей в JVM. Поддержку конкретной выбранной модели, предобработки и лицензию необходимо проверять отдельно (T12).

Таблица 4. Способы запуска вывода за REST API на Spring Boot

| Критерий | ONNX Runtime внутри Java | Отдельный сервис вывода на Python | PMML / JPMML-Evaluator внутри Java |
| --- | --- | --- | --- |
| Сложность разработки | Экспорт всей поддерживаемой цепочки, имена / типы / формы тензоров, загрузка сессии | API на Python вокруг исходной модели; внутренний контракт, тайм-ауты и недоступность сервиса | Экспорт PMML, отображение схемы полей и проверка преобразований |

| Сопровождение | Backend и файл модели развёртываются вместе; версии предобработки и артефакта фиксируются | Два сервиса и два набора зависимостей; модель можно выпускать отдельно при согласованной версии | JVM и артефакт PMML; нужны поддерживаемый конвертер и проверенные версии |

| Роли команды | Али экспортирует и предоставляет эталонные ответы; Оралхан подключает среду выполнения | Али передаёт модель и среду; Оралхан обеспечивает контракт сервиса и эксплуатацию | Али проверяет экспорт; Оралхан — выполнение в Java; команда проверяет условия лицензии |
| Развёртывание | Приложение Java и нативная среда выполнения для выбранной платформы; сборку нужно опробовать | Java плюс процесс Python, закрытая внутренняя сеть, health / status и контроль ресурсов | Java и подходящие библиотеки PMML; отдельный процесс Python не нужен |
| Ограничения | Экспорт и численная эквивалентность пока не доказаны; данные пациентов не входят в тестовый артефакт | Дополнительная точка отказа; необходимо контролировать пакеты и происхождение артефакта | Совместимость не универсальна; проект заявляет AGPLv3 с альтернативным лицензированием по договорённости |

Условное предложение. Опробовать ONNX Runtime для Java на первом небольшом MLP / базовом методе. Утверждать путь только после успешного экспорта предобработки и модели и прохождения теста эквивалентности. Если экспорт ненадёжен или модели нужны неподдерживаемые операции, рассмотреть сервис на Python. PMML — резервная альтернатива для подходящих табличных моделей; он не выбран и не реализован. В backend для этого уже есть точка расширения: README предписывает заменить класс недоступной модели по умолчанию реализацией PredictionModel, у которой info() описывает точные входы предобработки, а predict() применяет ту же предобработку, что и при обучении, и возвращает фактически использованную версию.

ONNX нельзя называть «гарантированно безопасным» или «самым быстрым». Для всех вариантов артефакт должен происходить из доверенного источника, ресурсы — быть ограничены, а версии — согласованы. Для Python особенно важно не загружать недоверенные файлы pickle / joblib: такие механизмы могут выполнять код при загрузке. Это подтверждает документация scikit-learn (T11).

## 5. Проверка решения и критерии его пересмотра

Перед подключением реальной модели Али и Оралхан должны согласовать паспорт артефакта: модуль, цель и единицы, признаки и их порядок, предобработка, допустимые категории / пропуски, версия и контрольная сумма файла, версии библиотек и ожидаемые формы входа / выхода. Для временного модуля — также частота, окно, горизонт и правило состояния. README backend уже перечисляет те же пункты (схема признаков, артефакт, контрольная сумма, кодирование категорий, единицы, предобработка и примеры численного соответствия) как вопросы для согласования с Али до включения реального вывода. Это планируемые требования, а не существующий формат API.

Для приёмки интеграции предлагается контрольный набор синтетических и допустимых анонимизированных тестовых входов. Максимальное расхождение между офлайн-выводом и развёрнутым выводом должно укладываться в абсолютный / относительный допуск, утверждённый заранее; допуск обосновывается типом данных и смыслом цели. Конкретный допуск и успешная эквивалентность сейчас не заявляются. Ошибки схемы, единиц и версии должны обнаруживаться, а не превращаться в правдоподобное число.

Производительность необходимо измерять на названном оборудовании: загрузка артефакта, тёплый вывод и полный REST-запрос отдельно; фиксировать число запросов, размер входа, параллелизм, медиану / p95, ошибки и использование памяти. Тайм-аут frontend по умолчанию 15 секунд — клиентская настройка, а не измеренный SLA и не доказательство скорости модели.

Подход к интеграции необходимо пересмотреть, если экспорт не поддерживается, превышена согласованная задержка / память, нужен другой формат входа или ответы невозможно воспроизвести. Очередь задач, GPU, оркестрация контейнеров и дополнительные базы данных не объявляются обязательными без соответствующего требования.

## 8. Границы достоверности

Альтернативные фреймворки и ML-библиотеки не устанавливались; обучение, преобразование в ONNX / PMML, нагрузочные тесты и тест Python / Java не выполнялись. Проверены содержимое репозитория, README backend и открытая первичная документация. Выбор технологии не заменяет проверку качества данных, независимую оценку модели и анализ рисков обработки медицинских данных.

На предварительной защите можно обосновать сохранение готового frontend, направление backend на Java, поэтапное сравнение базовых методов с нейронными сетями и критерии выбора способа вывода. Нельзя утверждать, что все три модуля работают, что форматы уже совместимы или что выбранная технология даёт клиническую точность.
